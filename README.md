# DHP-KEM — Reference Implementation

A Python reference implementation of **DHP-KEM** (Dual Hard-Problem Key-Encapsulation Mechanism), the hybrid KEM proposed in the accompanying CECY 321 project report

DHP-KEM combines:

| Component | Hard problem | Provided by |
|---|---|---|
| ECDH on Curve25519 | ECDLP | `cryptography` (OpenSSL-backed) |
| ML-KEM-768 / ML-KEM-1024 (FIPS 203) | Module-LWE | `kyber-py` (pure-Python reference) |

through a transcript-bound HKDF Extract-then-Expand combiner. The encapsulated session key remains pseudorandom as long as **at least one** of ECDLP and Module-LWE remains computationally hard (disjunctive dual-hardness; Proposition 2 of the report).

---

## Status: REFERENCE ONLY

This implementation is intended to demonstrate the protocol clearly and to provide a runnable testbed for the report's KATs and correctness arguments. **It is not production-ready.** The most important reasons:

1. **`kyber-py` is not constant-time.** Any production deployment must use a constant-time ML-KEM such as the implementations in [liboqs](https://github.com/open-quantum-safe/liboqs) or [pq-crystals](https://github.com/pq-crystals/kyber). See §8.1 and §9.2 of the report.
2. **No side-channel verification has been run** on the resulting binary (CT-Verif, ctgrind, Binsec/Rel — see report §9.2).
3. **No hardware-bound key storage.** Production use requires HSM/TPM integration as discussed in §10.2.
4. **DHP-KEM-LT is unimplemented** because no maintained pure-Python FrodoKEM library is available; calling `keygen(DHP_KEM_LT)` raises `NotImplementedError`.

## Quick start

```bash
# 1. Install dependencies (Python ≥ 3.10)
pip install -r requirements.txt

# 2. Run the test suite
./run_tests.sh

# 3. Run microbenchmarks
python -m benchmarks.bench --iters 100
```

A complete worked example:

```python
import dhp_kem

# Choose a parameter set (MODERATE / ADVANCED tiers — LT raises NotImplementedError)
ps = dhp_kem.DHP_KEM_128

# Bob generates a long-term keypair and publishes pk
keypair = dhp_kem.keygen(ps)

# Alice encapsulates a fresh session key K under Bob's public key
ciphertext, K = dhp_kem.encap(ps, keypair.pk)

# Bob recovers K from his secret key and the ciphertext
K_prime = dhp_kem.decap(ps, keypair.sk, ciphertext)

assert K == K_prime, "Decapsulation failed"
print(f"Derived a {len(K)}-byte shared key: {K.hex()}")
```

## What each test covers

### `test_combiner.py` (10 tests)

* `combine()` output length matches the parameter set's `L`.
* Determinism — same inputs ⇒ same `K`.
* One-bit sensitivity — flipping any bit of `ss_ec`, `ss_lwe`, `T`, or `ctx` changes `K`.
* Rejection of empty inputs.
* **RFC 5869 §A.1 Test Case 1 conformance** — our `hkdf_extract` and `hkdf_expand` agree on every byte with the IETF-published test vector for SHA-256.
* Cross-check that our two-stage `Extract+Expand` equals a one-call `HKDF()` from `cryptography`.

### `test_kat.py` (2 tests, 1 CLI sub-command)

Deterministic Known-Answer Tests for `compute_transcript()` and `combine()`. Vectors generated from a fixed SHAKE-128-derived stream and stored in `kat_vectors/dhp_kem_kat_v1.json`. A second implementation in another language can replay the same seed and check byte-for-byte agreement.

Regenerate with `python -m tests.test_kat --generate`.

### `test_negative.py` (5 tests)

Negative tests — every kind of input tampering must change `K`:

* flip one byte of `A` (ephemeral ECDH point)
* flip one byte of `c_lwe` (ML-KEM ciphertext)
* decap with a freshly-generated unrelated keypair
* encap under DHP-KEM-128 and decap under DHP-KEM-256 (should `ValueError`)
* transcript fields reordered ⇒ different `T`

### `test_correctness.py` (5 tests)

* 50 randomised roundtrips per parameter set (Proposition 1).
* `DHP-KEM-LT` correctly raises `NotImplementedError`.
* Length checks on `K`, `A`, `c_lwe`.

### `test_timing.py` (1 test)

A loose timing-sanity check on `combine()`. **This is not a constant-time proof**; it catches only crude branches that gate on secret bytes. Real verification requires CT-Verif, ctgrind, Binsec/Rel, or dudect — see §9.2 of the report.

## Benchmarks

Measured on a typical Linux container (pure-Python ML-KEM):

| Parameter set | Component KEMs | KeyGen | Encap | Decap |
|---|---|---:|---:|---:|
| DHP-KEM-128 | X25519 + ML-KEM-768 | ~ 3.0 ms | ~ 4.1 ms | ~ 5.4 ms |
| DHP-KEM-256 | X25519 + ML-KEM-1024 | ~ 4.5 ms | ~ 5.7 ms | ~ 7.4 ms |

These numbers are pure-Python and *not* representative of a production C/Rust/Go implementation, which would run 100–1000× faster on the ML-KEM half. See report §10.3 for projected performance with a constant-time ML-KEM in a real deployment.
